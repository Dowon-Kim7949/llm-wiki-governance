## A. LinkedIn (English)

AI coding agents now write a lot of our project documentation: architecture notes, feature
descriptions, requirements. Writing it is the easy part. The hard part is knowing which of it is
still true after the code moves.

I built llm-wiki-governance, an MIT-licensed, zero-dependency Node.js CLI that treats those
documents like code:

• Every document carries a review state. Agent-written docs stay `needs_review` until someone
  runs `review --approve`. The tool records the name given; it cannot prove who it was.
• Every document cites the files, line ranges or Markdown sections it is based on, and the CLI
  checks that each citation still resolves.
• In a pull request, `impact` names the approved documents whose cited code changed while the
  document did not. When an approved requirement changes, it lists the files that requirement
  links.

It works before any code exists (requirements and decisions recorded as planned knowledge) and on
existing projects. Runnable walkthroughs cover Vue 3 + TypeScript from an empty repository, a
Python FastAPI service and a React + Express workspace. The CLI needs no model and no API key.

What it does not do: check that a sentence is true, run your tests, or decide that a requirement
is implemented. Date-based drift detection has documented blind spots, and no independent
developer has run the usability protocol yet. The validation page lists what has been shown and
what has not.

[After the advisory is public: 1.40.0 also fixes a security issue in the MCP server and the
programmatic API. If you use either, upgrade.]

**Title:** Failing a PR when code changes but the doc that cites it does not

Agent-written docs drift quietly: the code moves in one PR, the document describing it is not
touched, and nothing fails. We tried to make that a CI signal without parsing any language.

The mechanism is deliberately simple. Each Markdown document declares what it is based on in
frontmatter: files, line ranges, Markdown sections, names. In a PR, `impact --since
origin/<base>` diffs the change set against those citations and lists the approved documents
whose cited files changed while the document did not. Under `strict` that is an error and the job
fails; under `standard` it is a warning; `lite` turns it off.

Things we learned the hard way, which may matter for anyone building something similar:

- **Checkout depth matters.** `impact --since` needs the base ref. A default shallow checkout
  does not have it, and the check degrades quietly instead of failing. We set `fetch-depth: 0`.
- **Release commits fan out.** Every release changes `package.json`, which many documents cite.
  A `version`-only change is now excluded from the comparison, but only when we can show nothing
  else changed.
- **Date-based checks are not merge-aware.** A branch reviewed before merging, then squashed,
  looks like a new change; a branch created before a review and merged after it can be missed.
  We document these limits instead of claiming the check is complete.
- **Narrowing to the cited lines can hide changes.** Comparing only the cited region against a
  date-based snapshot hid changes the reviewer never saw. Narrowing now requires the review's
  own commit to agree, and falls back to the whole file when it cannot tell.

Questions for others doing this:

1. How do you pick the baseline for "the state the reviewer approved" when branches are squashed?
2. Has anyone found a merge-aware signal cheaper than walking first-parent history?
